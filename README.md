# Diversity.ca

A bilingual English/Canadian French consulting website built with Astro and TypeScript. It produces static HTML, CSS and JavaScript for WHC Pro shared hosting; production does not require a persistent Node.js server.

The implementation follows [CODEX_MASTER_BRIEF.md](CODEX_MASTER_BRIEF.md) and [DEPLOYMENT_RUNBOOK.md](DEPLOYMENT_RUNBOOK.md). The full blue → purple → magenta wordmark and the approved people/opportunity/progress descriptor form the brand system. The website is an implementation for review, not a claim that the business, forms or production domain have been verified or launched.

## Run locally

Use Node.js **22.23.4 or later** and npm. Node 24 is used in CI. Astro is pinned to 7.4.4 and dependencies are locked in `package-lock.json`.

```sh
export ASTRO_TELEMETRY_DISABLED=1
npm ci
npm run dev -- --ignore-lock --host 127.0.0.1 --port 4321
```

Run these commands in the repository root. The development server starts on local port 4321; stop it with Ctrl+C. Astro's `--ignore-lock` flag keeps this server in the foreground when an agent is detected. It does not disable dependency-lockfile checks.

## Build and validate

```sh
export ASTRO_TELEMETRY_DISABLED=1
npm run check
npm run lint
npm run build
npm run budget
npx playwright install --with-deps chromium
npm test
```

`check` runs Astro and TypeScript diagnostics. `lint` checks formatting with Prettier; `npm run format` applies formatting when needed. `build` writes the static site to `dist/`. Playwright runs browser and HTTP checks against the built output, starting its own preview server on local port 4323. Run the build before browser tests.

The test configuration uses `CHROMIUM_PATH` if explicitly supplied, otherwise an installed `/usr/bin/chromium` when available, otherwise the Playwright-managed Chromium. The browser-install command can require system-package installation permission. Tests, dependency installation and browser installation must retain the environment's proxy and CA settings.

To inspect the production output manually:

```sh
npm run preview -- --ignore-lock --host 127.0.0.1 --port 4323
```

Test results go to `test-results/`, the HTML report to `playwright-report/`, and review screenshots to `artifacts/` when generated by the tests. These outputs are intentionally ignored by Git. Test definitions and CI configuration do not establish a passing result; consult the actual run and QA report.

## Site structure

- Equivalent `/en/` and `/fr/` journeys, with a root entry that redirects to English.
- Seven service divisions and 21 substantive subservice pages per language.
- About, approach, corporate and government solutions, procurement, industries, Canada-wide delivery, partnership, privacy and accessibility pages.
- Three original insights articles with translated content and editorial metadata.
- Proposal, assessment, training and general-contact enquiry journeys.
- Canonical and language-alternate metadata, a sitemap, robots policy, social-sharing metadata and a 404 page.

Content lives in `src/data/`; layouts, page components and styles live under `src/`. Public photographs, fonts and brand assets are served locally from `public/`. Photography is illustrative and does not depict Diversity.ca personnel, offices or completed work. Each distinct page has its own relevant image; English/French counterparts intentionally share that image. The collection combines 13 licensed photographs with 41 original editorial illustrations, including the 404 illustration. The five supplementary homepage visuals are exclusive to that page. Inclusive workshop, public-service and accessible-technology scenes complement genuine collaboration and community photographs; full-frame layouts keep people and assistive devices visible. Image uniqueness is tested by URL and file hash. See [research](docs/RESEARCH.md) and the [complete photo licence/source manifest](docs/image-provenance.json).

## Enquiries

Copy `.env.example` to `.env` only when configuring a real provider. The optional build-time variable is:

```dotenv
PUBLIC_FORM_ENDPOINT=https://formspree.io/f/your-form-id
```

Use the actual Formspree endpoint, not the example identifier. Only a valid HTTPS Formspree `/f/…` endpoint is accepted. `PUBLIC_` values are included in browser code, so never place an API secret, password or private key in this variable. Rebuild after changing it.

Without a configured endpoint, the form prepares an email draft for `info@diversity.ca`. It does not send mail or report a submitted enquiry; the visitor must send the message in their email application. Visitors can also download their enquiry as a local JSON file. That file is not uploaded to a CRM. The mailbox and delivery process still need owner verification.

With a valid endpoint, the form submits to the provider and shows success only after a successful response. Verify receipt, spam handling, errors and privacy disclosures before production. Sensitive attachments are not accepted by the public form.

Assessment enquiries can describe the scope, assets and known barriers. Training enquiries can specify audience size, roles, learning goals, delivery format and languages. Proposals can include the procurement reference, desired deliverables, constraints and a closing date/time with an explicit time zone. These additional details are optional; a supplied closing time needs its time zone. The general contact form adapts its questions to the selected service.

Service-page links carry allowlisted service/subservice identifiers into the relevant form and preserve that context when switching languages. Names, email addresses and free-text answers are never copied into those links or stored in the browser. Changing the active question group excludes its inactive fields from email, JSON and provider payloads. JSON exports use schema version 2, retaining common enquiry fields and adding stable identifiers, localized context and structured details.

## Sample deliverables

Every division and subservice page contains a distinct illustrative deliverable outline, a preparation checklist and scope responsibilities. These are scoping examples rather than completed client work. Each English/French page has a matching plain-text outline download at `/en/samples/<service>/<subservice>.txt` or its French counterpart; division downloads omit the subservice segment. The final contents are agreed in the proposal. All files are generated locally during the static build.

## Release review

Review [CONTENT-REVIEW.md](docs/CONTENT-REVIEW.md) and the [deployment instructions](docs/DEPLOYMENT.md) before publishing. Exact brand execution, bilingual content, business credentials, legal drafts, mailbox/form delivery and the final release require owner review. Unverified consultants, credentials, client results, offices and telephone numbers must not be invented.

The GitHub Actions workflow installs dependencies, checks types and formatting, builds and runs Playwright. It does not deploy the website or change DNS. Upload only the contents of a verified `dist/` build to the confirmed WHC document root after explicit production approval.
